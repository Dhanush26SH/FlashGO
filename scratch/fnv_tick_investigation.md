# F&V Task List — Daily Location Completion Tick Investigation

## 1. How Location Cards are Generated
In `mobile-staff/src/screens/Warehouse/FnvTaskWorkflow.tsx`, F&V tasks are generated by querying `product_batches` (where category is F&V and `available_quantity > 0`) and mapping them against `warehouse_product_placements`. This produces one task card for every physical location where a batch currently has inventory.

## 2. "Good / No Issue" Completion
When a user selects "Good / No Issue" and taps Confirm, the app shows an alert ("Success, Item marked as good. No inventory changed.") and clears the active task. **Zero database calls are made.** No authoritative record of this completion is persisted anywhere in the system.

## 3. Removal Completions
When a user selects "Rotten / Spoiled", "Damaged / Bruised", or "Poor Quality / Unfit", the app calls the `remove_fnv_batch_inventory` RPC. This succeeds and creates an authoritative `stock_ledgers` entry. However, as established in the previous investigation, this ledger entry **does not store the location_id**.

## 4. Does the System Have Enough Persisted Data?
**No.** The database currently has zero ways to answer “Has this exact batch/product at this exact warehouse location already completed its F&V inspection today?” because:
- "Good" inspections leave no trace.
- "Removal" inspections leave a ledger trace but lack the location identifier.

## 5 & 6 & 7. Semantic Differences and Inference
- The completion must be location-specific (same batch can exist at multiple locations).
- We cannot infer completion from inventory changes because "Good" causes no changes, and "Removal" changes inventory but without location context.
- Therefore, there is a fundamental split in persistence: "Good" vs "Removal" behave completely differently backend-wise.

## 8. Smallest Safe Way for a Daily Tick
Since existing data is mathematically insufficient and we cannot modify the database schemas or RPCs, the smallest, safest, and most robust solution for a daily visual ✓ indicator is **Client-Side Local Storage (`AsyncStorage`)**.

**Proposed Design (Option: AsyncStorage Cache):**
1. When a task is successfully completed (whether it is a "Good" short-circuit or a successful RPC "Removal"), the frontend saves a completion flag to the device's local storage:
   - Key format: `fnv_checked_${task.locationId}_${task.batchId}_${YYYY-MM-DD}`
   - Value: `true`
2. During the `fetchFnvInventory` loop, the app checks `AsyncStorage` for these keys.
3. The UI conditionally renders a small green ✓ on the card if the current day's key exists for that location+batch.

## 9 & 10. Daily Reset and Safety
- Because the date is embedded directly in the storage key (`YYYY-MM-DD`), the completion is strictly tied to *today*. Tomorrow, the date string changes, the key misses, the ✓ disappears, and the location naturally becomes eligible for visual completion again.
- This design requires **zero** changes to `remove_fnv_batch_inventory`, zero database migrations, zero SQL writes, and absolutely no changes to inventory semantics. It is a 100% safe UI/UX enhancement.
